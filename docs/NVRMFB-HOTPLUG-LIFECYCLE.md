# NVRMFB display hot-plug lifecycle

NVRMFB keeps the NVKMS display handle and framebuffer instance across cable changes. A disconnect confirmed by `getDynamicDisplayInfo` marks that instance offline, clears its cached EDID length and display-audio properties, and schedules the registered `kIOFBConnectInterruptType` handler after leaving the display gate. Scanout storage and the WindowServer surface remain allocated.

A reconnect restores the handle's current EDID and physical size, relights the existing head with `reflip()`, republishes current display-audio properties, and schedules the same per-framebuffer handler. The callback is owned by the framebuffer instance; `scheduleCall()` retains it for queued work and `stop()` cancels and drains that call.

`hasDDCConnect`, `getDDCBlock`, `kConnectionEnable`, and `kConnectionCheckEnable` reflect the offline state, so cached EDID cannot make a disconnected connector look live. If NVKMS omits a known handle from `getDisplays`, NVRMFB queries that handle directly: a successful offline result triggers the transition, while query failure or a connected result preserves the current state.

A card with one output and no display on it at start starts that output all the same, in the offline state above: macOS opens a GPU's framebuffers when WindowServer starts and does not look for one that registers later, so a framebuffer that started only when the monitor arrived was never opened and the monitor stayed dark until a restart. The output starts on a stand-in 1920x1080 raster that nothing is scanned out with; no mode set is tried while it is empty, and `connected-displays` on the display nub counts it, so the display stack is armed before WindowServer starts as it is with a monitor. The first monitor is taken up like a changed one (`takeFirstDisplay`, then `adoptSwappedDisplay`): its own mode at that raster replaces the stand-in, the head gets its first mode set, and the connect handler is called. The scanout memory is the size reserved at start (3840x2160), as for a changed monitor. With several outputs, or with the panel proxy (`nvfbigpu=1`), nothing changes; `nvfbemptyout=0` turns it off. `tools/test_fb_empty_output.py` checks the rule and the first-monitor path.

A GPU in standby or without power sends no display event, and NVKMS's resume asks no connector. When NVRM reports the GPU back (`NVRMGpuPower` 1), an output that has no display therefore runs the event's scan once, so a cable plugged in while the GPU was off is taken up as above; an output that has its display is only lit again. `tools/test_fb_gpu_back_scan.py` compiles the handler and counts the scans.

Run `python tools/test_nvrmfb_hotplug_lifecycle.py` with `clang++` available. The check compiles extracted production methods and inspects the production transition path; hardware hot-plug behavior still requires runtime validation.
